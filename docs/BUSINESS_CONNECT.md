# Business Connect — owner-controlled text profiles

South Africa MVP: /business-connect uses the existing in-memory Luqi account session to save durable MySQL drafts; /businesses and /businesses/:id provide anonymous public search and shareable profiles; /business-connect/review is restricted to explicitly assigned reviewers. A Luqi profile is not CIPC company registration or a trading licence. No business is seeded in production.

## Publication and privacy

Drafts remain private through the application. The owner chooses visibility separately for phone, email, website, public storefront address and pricing. Service-area and mobile profiles cannot store an exact address in the address field; all text warns against home addresses. A saved preview contains only proposed public fields. Review submission fails closed until an active reviewer is assigned; private drafts remain usable. At least one selected contact channel and a versioned owner-authority/publication-consent acknowledgement are required for review. Only an assigned reviewer can approve the pending saved revision; no self-review. Reviewer authority is a dedicated, SELECT-only runtime table, independent of existing account roles and P2P eligibility. The web API cannot appoint reviewers.

Reviewers see proposed public fields and reports, not unchecked private contacts. Review approval attests publication safety, including adult/guardian/business authority through an approved private process. No identity documents are collected here. Publication review never certifies contacts, exact location, licensing, quality, CIPC status or external-provider verification. These distinctions remain visible on every public profile.

Saving edits withdraws the published snapshot and requires review again. Pause withdraws immediately for fresh API requests. Delete physically removes the owned profile and cascading active reports/audit from primary storage after explicit confirmation; backups and previously copied public material are not erased by that action. Daily counters remain for abuse prevention. No photos, device GPS points, credentials, bank details or customer records are collected. No AI or paid map service is called. A clicked Google Maps address search sends only the approved public storefront address, not a customer starting point.

## Durability, concurrency and abuse

Six additive InnoDB tables: schema digest marker, reviewer assignments, profiles, metadata history, daily usage and profile reports. Foreign keys cascade correctly; the digest and index checks refuse unknown/partial schema adoption. All runtime grants are table-specific; metadata/reviewer tables are SELECT-only. No DDL or reviewer assignment is reachable through HTTP.

Account row locks serialize owner writes across replicas; UUID creation and expected-revision comparisons prevent stale overwrites and duplicate retry publication. Writes are never automatically retried. Publication decisions use a database-scoped named mutex and recheck current authority, state, revision, consent and possible public duplicates. Different reviewers cannot accidentally race duplicate approvals. An explicit duplicate check is required before approving a known match. Owner duplicates are rejected without exposing another account's private data.

Limits are per account, not shared public visitor limits: 10 owned profiles; 200 confirmed owner/profile changes per UTC day; 5 report submissions per UTC day; assigned review operations have a 2,000-change daily safety ceiling. Public search is account-free with pages of 20 and keyset pagination. It uses a full-text index plus province/category filters, fixed identifiers, parameter binding and four-second statement deadlines. Reports do not automatically remove a listing by volume; an assigned reviewer records a decision. The API never returns raw driver errors.

Minimal counters and undecided reports become eligible for deletion after 31 days, metadata history after 90 days. Each profile also keeps at most 100 recent history entries, without draft/content copies. The enabled production web process runs bounded hourly cleanup (up to ten batches of 1,000 rows per table); interruption or feature disablement can delay cleanup. Owner drafts remain until deletion. No claim of immutable audit, zero backups, legal-compliance certification or guaranteed moderation response is made.

## Capacity and budget

1,000 prospective owners can each prepare a profile, and the per-account profile ceiling permits up to 10,000 profiles across them. This is an application bound, not a measured concurrency claim. Public visitors do not consume this owner ceiling or the guest AI reply allowance. A typical text draft/public snapshot pair is a few kilobytes; allow roughly 10–15 MB per 1,000 profiles including basic indexes, plus bounded history, report and counter storage. Maximum-field and adversarial workloads can be materially larger; measure actual MySQL storage/latency before larger rollouts. No model inference, paid geocoding, payment activation, external map edit or AI budget change occurs. The one-off operator image uses normal existing Railway build/compute billing and exits; it is not an always-running additional application service.

## Operator rollout

1. Pass exact-head unit, real MySQL, isolated operator-image and real two-account Chromium/WebKit journeys. Keep the production feature flag absent/false.
2. Build ops/Dockerfile.business-setup from the reviewed commit in a private, source-pinned one-off Railway service named luqi-business-db-setup, in the existing kind-spontaneity production project. No public domain, volume, healthcheck or listener; restart policy NEVER.
3. Wire DATABASE_URL by reference to web.DATABASE_URL and LUQI_DB_OPERATOR_URL to MySQL.MYSQL_URL. Privileged credentials belong only to this isolated operator service, never to the web API or source. Set LUQI_DB_CHECK_SOURCE_SHA to the exact reviewed source commit. For explicit creation only, set LUQI_BUSINESS_SCHEMA_INTENT=create-absent-business-storage-v1.
4. The job checks project/environment/service/source identity, the dedicated existing runtime identity, core schema, absence or exact validated business schema, bounded DDL digest, foreign keys/full-text index and table-only grants. It creates only the six new tables, inserts their digest metadata and grants their exact runtime privileges. It does not change existing customer rows, account roles, identities, AI budgets or production flags. Partial/mismatched storage fails closed; never drop/rebuild it automatically. Rollback disables the business feature while retaining data for review.
5. Require terminal job success and its aggregate validated result. Enable LUQI_BUSINESS_CONNECT_ENABLED on the web service only after storage/grants are proven; deploy the tested main revision and verify release identity plus anonymous and authenticated behaviour.
6. Owner must identify and verify the person/account responsible for publication review. A trusted operator may then assign luqi_business_reviewers_v1 for that existing account using a reviewed private operation. No reviewer is guessed or auto-appointed, and no existing users.role is replaced. Confirm moderation coverage, corrections and privacy handling before processing real publication requests.
7. Run a real-business/customer-device acceptance with owner-approved material before promoting reviewed businesses. CI fixtures are not production customers or business evidence. Photos, GPS pin verification, delegated staff, formal company registration and external map listing workflows remain later phases of issue #360.
